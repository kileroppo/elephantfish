## 介绍 

elephantfish 是受到 [sunfish](https://github.com/thomasahle/sunfish) 启发而撰写的纯python的中国象棋引擎，核心代码只有几百行（见 [elephantfish.py](elephantfish.py)）,棋力方面我仅进行过其与象棋小巫师傻瓜难度的一场对局，在我测试的对剧中，elephantfish赢得了比赛。

在几天前看到了[sunfish](https://github.com/thomasahle/sunfish)这个项目(是一个国际象棋引擎，只有111行)，觉得很有意思，于是做了一个类似中国象棋版本，中国象棋和国际象棋略有不同，我仅仅单独完成了棋规部分，子力价值表直接的参考了 [象眼](https://www.xqbase.com/league/elephanteye.htm) ,mtd search部分的代码由于原版sunfish写的非常通用，我也就一行未改。

如果你对于程序中的mtd search看不懂建议先看一些对弈基础理论,比如articles下的几篇文章，如[对弈程序基本技术](articles/对弈程序基本技术.pdf)，其官方网址：https://www.xqbase.com/computer/outline.htm

elephantfish默认会进行5秒钟的思考，当然实际一般会比5秒多一些，如果你想要它进行更长时间搜索以获得更好的性能可以对源码相应位置进行更改。

如同sunfish一样，我认为elephantfish会是一个很好的平台，由于其代码非常少，可以很方便的进行各种实验，希望各位感兴趣的同学可以尝试对其进行优化. 如果在优化后想要评估和目前版本的棋力差别，可以使用 `tools/arena.py` 中的 self_arena 来将你的代码和elephantfish进行对弈。

如果你觉得这个版本的象棋ai实力不够强，可以看看 [XQpy](https://github.com/bupticybee/XQPy)

# 运行elephantfish!

elephahtfish 自包含在 `elephantfish.py` 文件中，只是用了python的自带操作而没有使用任何第三方库. 建议使用 `pypy` 或者 `pypy3` 来获得更好的性能表现.

简单的使用命令```python elephantfish.py``` 或者```pypy elephantfish.py``` 就可以运行象棋程序,程序会利用自带一个命令行工具进行对局.

## 转述对局台（Web UI）

如果以 Web UI 方式下棋，直接用启动脚本（首次会自动构建前端）：

```bash
start.bat           # Windows：双击即可
./start.sh          # macOS / Linux：可指定端口，如 ./start.sh 8020
```

脚本会自动找 Python、按需构建前端、拉起服务并打开浏览器。默认端口 8010；若它已被别的程序占用，脚本会先认出占用者不是本服务，再自动往后顺延一个空闲端口，不会把页面开到别人的接口上。服务跑在当前窗口，按 `Ctrl+C` 停止。

也可以完全手动：

```bash
cd frontend && npm install && npm run build     # 构建前端，只需要一次
python server/app.py 8010                       # 启动服务
```

浏览器打开 `http://localhost:8010/` 即可。

### 让同网段的其他设备访问

服务默认只绑 `127.0.0.1`，手机、平板、另一台电脑是打不开的。要放开：

```bash
start.bat 8010 lan              # Windows
EF_HOST=0.0.0.0 ./start.sh      # macOS / Linux
python server/app.py 8010 --host 0.0.0.0   # 手动
```

启动后控制台会把本机的所有可用局域网地址打印出来，用 `http://192.168.x.x:8010/` 打开即可。Windows 上第一次可能需要允许防火墙放行（Python 的入站规则）。

没有登录和鉴权，**同网段任何人都能打开并操作棋盘**，用完记得停掉。

### 这个界面是干什么的

它不是「人和引擎下棋」的界面，而是**让人当信使**的界面：

```
对手大模型下一步棋  →  人把这一步录进棋盘  →  引擎算出应手
→  人把应手喂回对手大模型  →  循环，直到将死对方
```

所以整个界面围绕「录入对方走法 / 取走我方应手」这两件事设计。**录入以棋盘为先**：

- **直接摆子**：点棋盘上的棋子、再点落点；或者按住它拖过去。轮到的子有抓手光标，可走的点会亮起来，拖到哪个点哪个点张开。这是最快的一条路 —— 不需要把棋步翻译成任何符号；
- 引擎在算的时候，盘面上会铺一条淡淡的虚线，那是它正在盘算的一步；它一落子这条线就撤掉，只留墨痕；
- 习惯键盘的人，也可以在转述台①里敲坐标（`h2e2`）或中文记谱（`炮二平五`），输入前几个字符就出候选，`Tab` 补全、回车落子。焦点只对「键盘流」自动跟随：一旦你开始用棋盘，它就不再每手来抢；
- 引擎算棋的时候**照样能输入**：抢录的那一步会排队，引擎一收手自动落子，人不会被计算时间卡住；
- 右侧「引擎应手」一点即复制，直接粘回对手模型；
- 对手模型若提供 HTTP 接口，在「对手模型接入」里填上地址就能半自动拉取。空闲时界面留了一秒一次的慢心跳，别的标签页、或对手接入把局面推走，这边也看得见。

目录结构：

```
engine/            引擎内核（棋盘表示 / 搜索 / 记谱 / 对局状态机）
engine/engine.py   引擎接缝：两个 adapter + 「选哪个 / 谁可用 / 怎么降级」
server/session.py  对局会话（一局棋 + 一个引擎 + 一次在跑的搜索）
server/store.py    对局存档（SQLite：每一局的棋谱与评分 + 跨重启的累计账）
server/app.py      转述对局服务的 HTTP 外壳（路由 / 状态码 / 静态资源）
frontend/          Vite + React + TypeScript 界面
tools/arena.py     新老引擎回归对局（速度对照；棋力结论请改用 arena2，见上方说明）
tools/arena2.py    对局度量台：固定节点预算的 A/B + WDL/Elo + 95% CI 晋级闸门
tools/verify.py    引擎一致性回归自检（棋规 / 记谱 / 主变 / 战绩 / 并发 / 存档 / 判分 / 度量台）
tools/smoke_http.py HTTP 契约自检（路由 / 状态码 / 字段 / 排队 / stale / 落库）
.devtools/         界面自检脚本（见下方「界面自检」）
review/            自检与质量迭代报告
```

原版 `elephantfish.py` **原样保留，作为棋力基准与回归 oracle** —— 它不是遗留代码：
`engine/core.py` 继承它的 `Position`，`tools/verify.py` 的走法生成对齐段拿它逐条逐序比对。
文件头有同样的说明。

对局逻辑与 HTTP 分开，图的是**测试面**：`server/session.py` 可以被直接实例化，
于是「引擎收手后排队那一步会不会落地」「搜索在飞时换局会不会把棋落到新对局上」
这类问题能写成普通断言；`server/app.py` 只管解析请求与写响应，由 `smoke_http.py`
走真实 HTTP 验契约。两边不需要为了测试对方而将就。

```bash
python tools/verify.py      # 引擎回归：棋规 / 记谱 / 主变 / 战绩 / 接缝 / 并发 / 存档 / 判分 / 度量台（~144s，203 条断言）
python tools/smoke_http.py  # HTTP 契约：路由 / 状态码 / 字段 / 排队 / stale / 落库 / 判分 / 错题本（自动找空闲端口，83 条断言）
```

### 每一步都判分：录棋的那个人也在长棋

界面不该只是一台记录仪。轮到你走的时候，服务会用**空闲算力**把眼前这个局面
的前几名搜一遍（默认 1.5 秒 / 14 层 / 3 条线，都在设置里），你落子之后当场对答案：

- 棋谱里**人走的每一手**带一个名次与差值 —— 正解、第 2 名、还是没进前几名；
- 差值算在**走子方视角**上，红方视角只用来画走势线。黑方亏的一步若按红方视角相减，
  会被念成红方涨了 —— 那不是精度问题，是「好棋」和「漏着」整批互换；
- 这个数**能不能当真**跟着一起来：两条线都是全窗精确值才说「差 1.4 兵」；
  截断来的分数只说「至少差 / 至多差」；两边都是界就只报名次不给数；
  「正解」这个词也只留给证得出精确差值的第 1 名，其余一律说「引擎第一选择」——
  名次是引擎的排序，正误是另一件事，措辞出口在 `frontend/src/lib/format.ts` 一处收着；
  有一条是杀棋就不谈兵数，只谈还有几步（方向看分数符号：被将死的一方也有一条杀棋线，
  照字面念成「错过 N 步杀」会把守不住的东西教人去攻）。内置引擎对试探失败的根着法
  交回的是上界，同分时差值会正好算成 0 —— 所以「差 0 兵」这句话在这台引擎上几乎永远
  是假的，界面上那一种只出现名次；
- 「差多少」之外还有一句**为什么**（`format.ts` 的 `whySentence`）：服务端把两条主变里
  **第一次吃到子**的那一手算成事实存进 `review.reason`（第几步、谁吃的、吃了什么），
  那句只报这件盘上真会发生的事，不再报一遍数字。三条边界划死了：这一手没进排名线
  就没有可比的主变，整句不说（「没看过」绝不能被念成「看了、都不吃子」）；两条线几步内
  都不吃子时只能说「给不出吃子层面的原因」，不许归因到「位置」这种这份数据证不出的东西；
  而**先吃到子的那一方照样可能是更差的一手** —— 那种形状必须明说「差的不在吃子上」，
  因为「能吃子所以该走这手」正是输入棋的人最容易形成的错觉；
- 人这一步的分数从此不再空着：评估曲线以前只有引擎那半边，现在两头都有点了。

判分只在引擎真正空闲的那段时间里跑：轮到引擎时不开场，引擎正在算时不开场，
同一时刻只容一条搜索 —— 抢不到就这一手**干脆不判**，绝不排队把应手拖晚。
人一走就停。开关是设置里的 `analyze`（连同 `analyze_ms` / `analyze_depth` /
`analyze_width`），关掉它是真不搜，不是只把面板藏起来。

每一手的判分整份写进存档（`plies.review`），因为后面要拿它做错题本与开局统计，
而那时候要问的是「**这个局面**你错过几次」，不是「第几手」。

### 错题本：把判分按局面攒成一道题

`GET /api/mistakes` 跨历次对局读那本存档，把人走的、带判分的手按 `fen_before` 聚成
题目（同一个位置在不同局、不同步数上会归成同一道题，因为 `nt.to_fen` 交回的串里
halfmove/fullmove 恒为 `0 1`）。右栏最下面那块列的就是它：错过几次 / 走过几次、涉及
几局、最差那次的判分与正解那手。三条口径值得写在这里，因为它们是这块面板的全部价值：

- **「算不算错」只写在 `server/store.py` 的 `review_verdict` 一处**，界面与自检都从它
  派生。`exact` 与 `at_least` 计入（后者证到了「这一手确实更差」，只是大小是个下界，
  措辞那一侧本来就有「至少」兜着）；`at_most` / `uncertain` / `below_top` **不计入**
  —— 那几个数证不出「更差」这件事，报进错题就是没证出来的比较。杀棋单算一档，因为
  它改变的是性质而不是程度，跟兵数不是同一把尺。
- **宁可少报几题。** 判不清的那几次如实归到「看不准」（按 `loss_kind` 分开报数），
  面板末尾那句话就是为它写的：没列进错题**不等于**下对了。
- **挑「最差那次」先比档再比大小**（`(2, 杀棋)` 压在 `(1, 兵数)` 之上）：慢一步杀该排
  在差九兵前面，两条断言钉着它 —— 一条把两者摆在一起比（把档位改回单个数字，红的就是它：
  `2 vs 900`），一条守兵数那一档内部仍是同一把尺（差 140cp 打得过差 40cp）。

只读、不写库、不进 130ms 那条轮询（只在页面装载时发一次，之后要按「重读」才再读）；
一题最多列 60 道（`MISTAKE_LIMIT_DEFAULT`），总数照实在 `summary` 里报，不受封顶影响。

### 复盘台：把存档里那一局一手手摆回盘上

错题本答的是「这个局面你错过几次」，答不了「那一局究竟是怎么走到这个局面的」——
重下一手漏着的棋要的不是那道题的答案，是从第一手起的那段来路。所以有了复盘台：
一块盘、一行棋谱、一手一句「为什么」（措辞仍然只从 `lib/format.ts` 出来）。

两个入口：右栏的**复盘架**（`GET /api/games`，一局一行，点一行开台），和错题本每题
那颗「摆到盘上」（直接跳到题上「最差那次」那一手 —— 比的是走法本身，不是手数，
否则默认落在第 1 手时两者撞上什么都证不出来）。

三条纪律，每条都对应 `replay.mjs` 里的一票：

- **只读，而且只读存档**：数据全部来自 `GET /api/game`，一眼都不看会话实况。底下那局
  照旧走、照旧每 130ms 刷它的盘，关掉这层就回到原位 —— 回放一局不该改变任何一局。
  这条不是装饰：`tools/smoke_http.py` 第 12 段与 `replay.mjs` 都拿「翻来覆去之后
  `/api/state` 逐字段相同、一个写请求都没发」钉它。
- **不搭那班车**：复盘架与错题本只在装载和按「重读」时各读一次，绝不挤进轮询。
  空闲时这页面压根不轮询，所以这一条只能在引擎应手那几秒的**忙碌窗口**里量。
- **一块盘一把尺**：台上那块盘复用现场那块的 `.board-wrap` + `.board` 几何。窄屏响应式
  里那两条改 `.board-wrap` / `.board` 的规则必须限定在 `.stage` 之内 —— 不限定就会串进
  这一层：`order: 2` 把进度按钮排到盘的**上面**，`height: auto` 把盘的尺换成按宽度算，
  实测 1024 那一档盘被 `max-width` 压成 578×695（比例 0.832，现场那块是 0.9000）。
  台子给这条链的头是「宽度算高、再收进栏高」（`.replay-board-wrap`），四档视口量下来
  都是 0.9000。

`lib/replay.ts` 里那条把身份号带下去的行棋线是这一层的手感所在：回放要的是「每一手
只有那颗走着的子换格」，所以每手的 `pieces` 沿用上一手的 `id`。换了节点 = 整盘被当成
换局面 = 集体瞬移，画面对了但没动 —— 而没有任何一条几何断言会为此变红，所以
`replay.mjs` 直接把那颗子的 DOM 节点攥在手里，看滑过去的是不是**同一个**节点。

视角只有一条约定：我方朝下，跟现场那块盘同一个朝向（引擎执黑 → `flipped=true`）。
它不跟着「走进来看的那一手是谁走的」跑 —— 跟着行棋方翻会出现「盘上已经走了一步、
数却写着 0」那种数与像对不上的开局。想换个视角看这一局，有那颗「转」。

### 界面自检

`.devtools/` 下是一套 Playwright 自检，一条命令跑完：

```bash
cd .devtools && npm install   # 只需要一次
npm test                      # 自己起服务，跑完自己关掉
```

`npm test` 就是 `node run.mjs`：挑一个空闲端口起 `python server/app.py`、等 `/api/health`、
依次跑八套脚本、汇总退出码（有失败就非零退出）。所以**不必先手动起服务** ——
以前得先开服务再跑脚本，忘了开只会得到一堆连接错误。

```bash
node run.mjs --port 8040      # 指定端口
node run.mjs --only drag      # 只跑一套
EF_PYTHON=py node run.mjs     # 指定解释器（默认 python）
npm run test:api              # HTTP 契约（tools/smoke_http.py）
npm run test:all              # 界面 + HTTP 一起
```

| 脚本 | 管什么 |
|---|---|
| `audit.mjs` | 四档视口的溢出 / 点击目标尺寸 / 控制台错误 / **回合条净空**（药丸装不装得进它自己那一行、棋盘垫会不会盖住它），外加交互场景与抢录竞态 |
| `drag.mjs` | 拖拽落子与点击落子两条路，坐标由棋盘框 + `data-flipped` 算出，视角翻转后照样成立 |
| `kbd.mjs` | 键盘走子通路（方向键移光标 → 回车选中 → 回车落子） |
| `frames.mjs` | 量一次落子/拖拽的主线程代价，并断言棋子的位移确实走 `transform` 而不是 `left/top`（后者是布局属性，每帧重排 + 重绘）。判据是**确定性**的：读真实棋子的 `transition-property`、读 `left/top` 是否为 `0px`、再改一次 `--cx` 看棋子是不是真的横移了一格。trace 采到的 `Layout`/`Paint` 事件数只打印、不作阈值（headless 下绝对值会飘，拿它当断言必然偶发变红） |
| `motion.mjs` | **动效还在不在。** 动效是最容易悄悄退化的一类东西：删掉一条 transition、把编排的 delay 抹平，页面照样能下棋，上面五套几何/位移断言一条都不会红。这套专守手感，十八条断言：①开场三段成序列（顶栏 → 回合条 → 棋盘，`animation-delay` 必须递增）②棋子落盘成波次（`pieceEnter` 的 delay 至少 3 档、最大 #### 别在一个还在动的东西上量尺寸

界面到处都是动画，而 `getBoundingClientRect()` 返回的是**当前**（可能正在动）的位置。
两条由此修出来的规矩：

* **量之前先等它站定。** 棋子的滑行走 `transform` 过渡（按跨度分级 210~360ms），
  盘面进场还有 620ms 的位移动画。`_contract.mjs` 的 `squareCenter` / `calibrate` 因此都走
  `steady()`：反复读，直到**连续两帧一致**才拿来用。`calibrate` 还更进一步 ——
  把「盘面框 + 棋子框 + 翻转 + 滚动」放进**同一个 `page.evaluate`** 里读，
  同一帧内完成，中间插不进一次重排或滚动，两次读数必然同源。
  不等就量，会把「量早了」报成「`lib/board.ts` 的几何常量改了，去同步 `_contract.mjs`」——
  排查方向完全错。
* **别拿固定 sleep 当同步。** `audit.mjs` 那一拍「引擎思考中」原先
  `waitForTimeout(350)` 再采一次 `task.status`。实测：引擎进 `running` 很稳
  （约 45ms），但**结束**时间在 347~991ms 之间飘 —— 皮卡鱼搜到 `max_depth`
  就收手，不一定用满 `think_ms`，于是窗口是 `min(think_ms, 深度到顶)`，
  最短只有 300ms。350ms 那个采样点正好卡在最短一档的刀刃上，8 次里红了 2 次。
  现在改成**轮询**到「引擎 running + 盘面有主变虚线」再截图，窗口再窄也抓得住。
* **截图必须自己造局面。** `shot.mjs` 原先不重置对局，截图内容取决于服务端当时停在什么
  局面 —— 于是同一份代码，第二次跑出来的图跟第一次不是一回事。更糟的是它用
  `legal_moves[0]`（引擎列出的第一个合法着法，通常是步臭棋）连走几手，对着同一个服务
  连跑两轮之后我方就被将死了；此时合法着法为空，`legal_moves[0].iccs` 直接抛异常，
  `thinking` / `help` 两张图再也出不来 —— 而因为第一轮的图是好的，这个烂法悄无声息。
  现在每一段都先 `reset` 一局。

棋子的位移与落子反馈现在的写法：

- **位移**：棋子在板面坐标系里只交出中心点（`--cx`/`--cy`，板面像素），由 CSS
  乘 `--u` 换成真实像素、走 `transform` 过渡；拖动时该过渡关闭（跟手）。滑行时长按
  跨度分级（210~360ms），缓动是纯减速、不回弹。没在动的那一帧 `--glide-dur` 是
  0ms，所以窗口缩放不会让棋子集体滑行。
- **时长必须锁住，不能按每帧的 diff 现算。** `--glide-dur` 由 `Board` 在**渲染期**
  写进一个 ref（`glideRef`），滑完由计时器收回。为什么：过渡要能起来，时长必须和
  「`--cx` 变化」落在**同一次样式重算**里。服务端够快时（本机十几毫秒），「本地预判」
  与「服务端确认」两次 React commit 会落在同一帧，浏览器整帧只做一次重算 —— 如果确认
  那一次已经按「这一帧没换格」把时长改回 0ms，浏览器看到的就是「起点 → 终点、时长
  0ms」，过渡根本不会开始。锁住之后两次 commit 的时长是同一个数，无论重算落在哪一次
  之后，过渡都会开始。**写成「只写不消费」是刻意的**：StrictMode 下渲染函数跑两遍，
  也只是把同一个值写两遍。
- **落子反馈**：由 `Board` 在**看着落定**那一刻（`landMs`，滑行时长的 7/8）给那颗子挂
  一次性的 `is-impact` 类（涟漪环 + 触盘压实 + 阴影收束），播完自己摘 —— 不再有
  `.piece.is-landing` 持久类，也不再靠 `.piece-face` 的 `key` 变化触发 React 重挂载来重播动画。
  为什么不是滑行**结束**：滑行终点是「样式收回」的时刻，不是「子落到桌上」的时刻；
  涟漪排到终点、音效排在 7/8，同一下落子就在画面上响两次。现在这两个定时器分工明确 ——
  `landMs` 那个只负责落点上的四样反馈（涟漪、落点框、残影、音效），`glideMs` 那个只负责
  收 `glideRef` 并强制落定。
- **吃子有因果：被吃的那颗一直看得见，直到落地那一拍才被撞飞。** 以前预判那一帧
  `game.pieces` 里它就被摘掉了，而攻击子还要滑 210~360ms —— 「被撞飞」发生在一颗
  两百多毫秒前就消失的子上。现在它挂着 `.is-doomed`（压在游戏子底下、点不到、稍暗）
  一路留到落点，服务端确认之后由**替身**接手：替身是渲染期从这一手的记录现推的，
  写成 effect 就晚一帧，那一帧画面上是「子还在半路、落点已经空了」。落地同一拍，
  替身换成带动量的残影（`pieceKnockback` 往撞击方向飞出 26 板面像素 + 翻 3~7 度）。
  摘掉与撞飞都在 `landMs`，悔棋 / 取消 / 卸载这条链上的定时器一起清干净。
- **时长只有一份定义**：`glideMs` 住在 `lib/board.ts`，`Board`（棋子滑行）与
  `useGame`（落子音效）共用它 —— 音效用 `landMs()`（= 滑行时长的 7/8，缓动纯减速、
  走满 7/8 肉眼已到位）来定那一刻。原来那里写死 210ms，是按固定的 240ms 位移配的；
  位移改成按跨度分级之后远手会滑到 360ms，死数就会在棋子还在半路上响一声。

- **开场是编排过的，不是「一起淡入」。** 顶栏（0ms）→ 回合条（140ms）→ 棋盘（180ms）
  按段落后手，棋盘升起的同时 32 颗棋子从近端一行行向远端落盘（行间 56ms、行内每颗 6ms，
  共 32 档 delay，压轴 948ms 收干净）。曲线用 `--ease-enter`（尾段极长的减速）——
  棋盘是「放」在桌上，不是「滑」到桌上。**编排只在首渲染发生一次**：`bootedRef` 一置位
  延迟恒为 0，重开 / 悔棋 / 换边都不再重播，否则每点一次按钮全场都要重新演一遍。
  三条硬指标由 `motion.mjs` 守着：段落的 delay 必须递增、落盘 delay 至少 3 档、
  压轴 ≤1200ms（还有一条下限 300ms —— 把编排关掉后 tail 会掉到 0，只卡上限等于没守）。
- **可走点也是荡开的。** 选中一颗子之后，它的可走点按 `--i` 每颗晚 18ms 出现，
  从选中那颗向外一圈圈铺开；`target-capture`（吃子位）另走循环脉冲。
- **应答链每一步都有回应。** 应手区三态（等待 / 思考 / 应手）互换播 200ms 的
  `heroSwap` 淡入上浮，思考态的底色与描边是**染**过去的（transition）不是跳过去的；
  排队条从应手区下面 `rise` 长出来；录完一手，应手卡 `stampIn` 盖印、棋谱最新一手
  同步盖印 —— 「你录了 → 它在算 → 它给了」这条链上每一环都是可见的。
  收起录入栏时 `type-toggle-btn` 会重新挂载，回来也得 `fadeIn`，不能闪回来。
- **开有关都要被看见。** 弹层（帮助面板、终局面纱）关掉时不再一帧摘掉：
  `hooks/useExitPhase` 让组件在关闭请求之后多活 180ms，期间挂 `is-leaving`
  播退场（面纱淡出、纸片往回沉、印章抬起来离开），播完才真卸载。
  同一只钩子也管**盘上的可走点与选中月牙环**（`Board` 里给 170ms）：落子那一刻取消选中，
  那十几枚点以前是「啪」地没的，现在各收回去一程（点往里缩、环往外散 —— 环套在子外面，
  往里缩会被看成被那颗子吸进去，而它正好在这一步离开）。退场这一程必须接着画**最后那一组**：
  `picked` 一空，`targets` 现算就是空数组，照现在的值渲染等于第一帧就什么都没了，
  所以那两组要冻在渲染期写的 ref 里（跟落点替身同一套规矩，换成 effect 就晚一帧）。
  为什么单写一个钩子：条件渲染的组件在状态转 false 那一帧就从 DOM 上没了，
  CSS 里退场动画写得再漂亮也来不及播 —— 入场有编舞而退场一刀切，手感立刻不对等。
  钩子里两处细节是踩出来的：**退场能被重开打断**（180ms 内又被叫回来要立刻清定时器，
  否则它会半路自己消失）、**卸载后不再动状态**（定时器必须进清理函数）。
  只断言「有没有挂 `is-leaving`」会被骗 —— 挂了类没播动画一样过，所以 `motion.mjs`
  还读 `animation-name`，并注入 `animation:none` 做牙齿检验。
  还有一层骗法只有量**收干净没有**才抓得住：类挂了、动画也真在播，但 CSS 时长与卸载定时器
  一样长，于是正收得最快时被摘掉。`is-leaving` 随 React 提交挂上，动画最早也要等下一次绘制
  才起步，天生晚一帧；退场又常常正好打断在**入场那波动画**上（落子前刚点过这颗子），同一元素
  换一条动画要多等第二帧才起步 —— `getAnimations()` 里连着两帧看到 `currentTime: 0` 就是这个。
  `--ease-exit`（`cubic-bezier(0.55,0,0.55,0.2)`）再把最陡的一段全压在末尾
  —— 两头一凑，140ms/140ms 那一程最后一帧还停在 `opacity 0.72`，眼睛看得见那一下被剪断；
  110ms 配 140ms 的定时器同样红（12 枚点**一枚都播不完**，实测到 ~154ms 才收干净）。
  所以盘上这两条动画是 **110ms**，比 `MARK_OUT_MS` 少 60ms ≈ 3.5 帧：先跑到 0，
  再靠 `both` 停着等卸载，剪子落在看不见的地方。
  自检问的是「`animationend` 发得出来吗」（12 枚点就该报 12 次）而不是「最后一帧的 opacity 多少」——
  后者是采样运气：最后一帧落在动画的哪一档全看帧边界怎么对齐，同一段退场两次量到 0.00 与 0.45，
  门槛只要往下压就误报（这条自己就被这么误报过一次）。动画自己报完工就没有运气成分，
  摘早了只会转成 `animationcancel`。牙齿：把这两条的时长改回跟定时器一样（170ms），自检立刻红 —— 12 枚点报 0 次。
  反过来它也给自检添了一个坑：**尸体照样带 `data-target`**，所以 `_contract.mjs` 的
  `target()` 与动效自检数点的两处都加了 `:not(.is-leaving)` —— 不然「选中一颗子数到几枚点」
  会把上一轮正在淡出的那几枚一起数进来（第 8 条就是这么被误判成「delay 全是 0ms」的：
  退场重写 `animation` 简写，delay 归零）。
- **翻转视角是「收窄 → 换 → 展开」，不是直接镜像。** 按 F / 点顶栏那个按钮时，
  盘面先用 `--ease-out` 收到 88% 宽（`boardTurn` 的 40%~58% 是个平口），换视角这件事
  放在第 150ms —— 也就是平口里，镜像这个跳变于是被藏进「几乎看不见宽度」的两帧；
  再用 `--ease-enter` 的长尾展开。`motion.mjs` 守两条：盘面最窄要 ≤0.97（真收窄了）、
  换视角那一帧的宽度必须 ≤0.97（换早了等于没躲）。**换视角仍然只有一个 state**
  （`flipped`），只是它现在被两个 `setTimeout` 夹住；转到一半再按 F 会被忽略，
  不叠第二段动画。
- **动画只许动合成器管得动的两个属性。** 一帧里 `transform`/`opacity` 只是搬图层，
  `width`/`left`/`margin`/`grid-template-*` 那类要把整棵布局树重算，`box-shadow`/`filter`/
  `backdrop-filter` 每帧重画一片区域 —— 落子那 360ms 里每帧都碰后者，手感就是那时候开始糊的。
  这一轮按这条清了盘上路径：落点框的旋转从 SVG `<animateTransform>` 换成 CSS（SMIL 既躲开
  `prefers-reduced-motion`，也躲开「引擎思考期间全站停摆」那张清单，等于盘上留着一个谁也
  管不着的常驻动画），光晕不再用 `drop-shadow` 而是多画一圈更粗更淡的 `stroke`；吃子脉冲
  只剩 transform + opacity；`.rail` 收起时补 `content-visibility: hidden`（抽屉合上之后
  栏里那几十行不该再参与渲染），`.board-surface` 加 `contain: layout style paint`
  （盘内的重排重绘被关在盘面这一块，不再往三栏网格外面漏）；顺手删掉 95 行早已没人挂类的
  「旅行墨点」CSS。第 17 条把它钉住（扫构建产物 + 真实 DOM），三处例外都当场论证过并写在
  选择器旁边：`.workspace` 的 `grid-template-columns`（抽屉开合本身就是宽度变化，
  且是离散点击、不在落子路径上）、评分条的 `width`（那一格是数值本身，缩放会把刻度拉花）、
  常驻的 `breathe`（五个 ≤16px 小点，每帧重绘不到 24×24）。
- **将军要在盘上说得出来，而且说在落定那一拍。** 声音早就报了（`useGame` 把它排在
  同一个 `landMs` 上），盘上以前只有一圈静态朱砂 —— 那圈说的是「还被将着」这个**状态**，
  于是「刚刚被将了」这个**事件**没有画面接住：一件事被做成了另一件事的附注。
  现在被将的王底下散出一圈朱砂环（640ms，只动 transform + opacity），由 `Board`
  的落点时钟在「看着落定」那一刻挂 `is-check-alarm`、到点自己摘（`CHECK_ALARM_MS`
  比动画多留 60ms，理由跟退场那一程一样：类挂上之后动画最早也要等下一次绘制才起步）。
  **为什么不直接拿 `.is-check` 驱动动画**：那是持久类，动画只在它从无到有时播一次 ——
  悔棋回到同一个被将局面不重播、轮询重渲染时也不该重播，更要命的是它播在服务端那一帧，
  比棋子落定早三百多毫秒，环都散完了子才落地。挂事件类而不是状态类，「什么时候播」
  才轮得到时序说了算。回调里读的是 `recordsRef` / `checkSquareRef` 而不是闭包：
  它跑起来已经是三百多毫秒之后，那会儿服务端的确认才刚到家。
  顺手删了一条空规则（`.app.is-thinking .piece.is-check .piece-face{animation:none}`
  管的那条动画根本不存在），并明确那一响**不进**思考停摆清单 —— 它就是这一步的汇报，
  停掉等于把消息吞了。棋谱那里补了 `scroll-behavior: smooth`：每手都
  `scrollTop = scrollHeight` 是硬切一屏，读到第 40 手时上一行还没看清就没了；
  减弱动效下把它压回 `auto` —— `scroll-behavior` 不是一个时长，
  底部那三条 `!important` 管不着它。

**「落子滑行时有时无」有两个真凶**，现象一模一样、成因完全不同，这一轮两个都修了。
光看现象分不出是哪一个，验证方式也不一样，所以两条断言各盯一个：

- **(a) 走子那颗被卸载重挂。** 判据曾经是
  `pendingMove && p.square === pendingMove.to && p.side !== game.turn` —— 本意是
  隐藏被预判吃掉的子，但**确认落地那一帧 `turn` 已经翻面**，走子那颗自己就满足
  「side ≠ 当前轮次」，于是连它一起被摘掉。同一颗子换了 DOM 节点，跑到一半的
  transform 过渡当场作废。修法：判据只认「它是不是正在走的那一颗」
  （`p.id !== pendingMove.id`）。验法：看节点是不是**同一个对象**（落子前打的标记
  还在、现在还连着文档、也确实落在落点上）—— 这是节点身份断言才抓得住的一种。
- **(b) 走子那颗的节点被 React 挪位。** 服务端 `pieces_of()` 是按**先列后行**排的
  （`engine/core.py`），棋子一换格它在数组里的下标就跟着变；React 对带 key 的子节点
  做重排用的是 `insertBefore`，对已经挂着的节点就是「先摘下来、再插回去」——
  **Chrome 在这种脱离/插回时会把该元素上正在跑的 CSS 过渡直接取消**（transitioncancel）。
  于是滑行取决于 React 这一帧决定挪走它自己、还是挪周围那一批。修法：渲染前按身份号
  排一遍（`piecesInOrder`），让 **DOM 顺序与棋盘位置无关**。验法：这一种**光看节点身份
  看不出**（同一个对象、结束后又连回文档、也确实落在落点上），只能看**位置轨迹** ——
  所以 `glide.mjs` 的位置断言（采样轨迹）是抓它的唯一手段。

**全站只有一盏灯，方向只写一次。** `tokens.css` 的 `--light-x`（0.42）是全站唯一的
投影横向系数。写法只有一条：每个投射影的横向分量都写成
`calc(<纵向位移> * var(--light-x))` —— 于是 calc 里 px 前面那个数字永远等于它后面那个
纵向位移的数字，扫一眼就知道角度对不对。三类豁免：`inset` 阴影（语义相反，是内壁受光）、
`0 0 <blur>` / `0 0 0 <spread>`（对称发光与描边圆环，本来就没方向）、字体墨迹的
`text-shadow`（给笔画加分量的排印手段，不是影子落在地上）—— 但真正表达凹凸的阴刻算
光影，要跟方向一致、**符号相反**（见 `.seal span`）。

**回合条的高度与净距是两条独立的前置条件，任一条不满足它都会被切掉。** 两个值都在
`tokens.css`：`--badge-h`（药丸的真实高度）与 `--board-clearance`（回合条与棋盘之间的净距）。

- `--badge-h` 必须**显式给**，不能指望内容撑开。窄屏（≤1140px）下 `.stage` 变成
  `display: contents`，回合条被上提进 `.workspace` 当成栅格的一行 —— 此时它内部 badge
  的高度**不参与该行的固有尺寸计算**（实测把 `min-height` 置 0，行高就是 0，而 badge
  仍旧 32px 杵在外面）。桌面档没上提，内容是正常撑开的，所以这个坑只在窄屏露头。
  原值是更早一版更矮的回合条留下的 26px；药丸长到 32px 之后，它就一直让药丸上下各溢 3px。
- `--board-clearance` 必须**大于棋盘垫的探出量**（`.board::before` 的 `inset: -14px`，
  手机档 10px）。棋盘垫比棋盘大一圈、**上缘也会往上探**，而垫子画在棋盘自己的层叠上下文
  里、棋盘又是 positioned 元素，于是整块垫子画在回合条**之上** —— 垫子那句 `z-index: -1`
  只压得住棋盘自己的内容，压不住回合条。净距不够 14px 时，垫子上缘就会把回合条下半截
  盖掉。桌面档走 `.stage` 的 `gap`，窄屏档走 `.board-wrap` 的 `margin-top`（窄屏
  `.workspace` 的 `row-gap` 是 0，而 `.stage` 已被拆散，那份间距得自己补回来）。

`audit.mjs` 在四档视口各量一次这两件事（`溢行` / `垫接入`，都要求 ≤0）并打印出来。
牙齿检验：把 `--badge-h` 改回 26px → tablet / phone 报「回合条溢出了自己那一行 3px」；
把 `--board-clearance` 改回 12px → 桌面 / 笔电 / 平板报「棋盘垫吃进回合条 2px」。

**空闲心跳不能带「对局进行中」这个门禁。** `useGame.ts` 在搜索停下时留一个每秒的
`/api/state` 慢心跳，好让「另一个标签页、或对手模型 HTTP 推来的局面」不会被漏掉 ——
它的注释也是这么写的。但条件原先写成 `state.game.status.state === 'playing' && !taskId`，
于是对局一结束（被将死 / 认输 / 和棋）心跳就自己关了，**而下一局同样是由外界开的**。
实测（`.devtools/_idle_heartbeat_check.mjs`）：对局进行中 4 秒内 4 次请求，对局结束后
4 秒内 **0 次**；外部随后开的新局界面 7 秒内毫无察觉，永远停在一个早已不存在的残局上。
换句话说，那个门禁恰好把心跳关在它最该工作的时候。条件只该是「我们没在搜」。
这个坑还是先把 `shot.mjs` 弄红才暴露出来的 —— 它当时的服务端正停在残局上。

- **🐘 象鱼内置（Elephantfish · 纯 Python）**：轻量级自包含教学/实验引擎，无任何外部二进制依赖。

在 Web 界面左侧控制栏的「引擎内核」即可随时一键切换两者。

**引擎接缝**（`engine/engine.py`）：两个引擎的差异关在两个 adapter 里，对外只有一个接口
`Engine.search(SearchRequest) -> Iterator[EngineInfo]`。接缝统一了三件一直散在调用点上的事：

- **参考系**。内置 `Searcher` 内部是「引擎视角」（黑方走棋时整个棋盘转过 180°），
  它的 `move` 是相对走子方的，而 `principal_variation` 又特意翻回了绝对坐标 ——
  这一个不对称，就是以前 `server/app.py` 里那句
  `abs_move = engine_move if red_to_move else flip_move(engine_move)` 存在的原因。
  接缝把 `move` / `pv` 一律定成**绝对坐标**，`score` 是侧方视角、`eval_red` 是红方视角，
  于是调用方一次翻转都不用写。
- **选哪个**。降级规则（偏好皮卡鱼但没装 → 落回内置）以前写在六处，各自重判一遍
  `engine_type == 'pikafish' and is_available`。现在只有 `EngineSet.active` 知道。
- **怎么测**。依赖是接受进来的，不是内部 new 出来的：`EngineSet(builtin=FakeEngine())`
  就能把真搜索整个换掉，`tools/verify.py` 的 H2 段就是这么验的。
- **一次搜索交出几层**。接缝允许一个 `SearchRequest` 交回多条 `EngineInfo`，每条带
  `multipv`（根着法排名，1 起）与 `bound`（`exact` / `lowerbound` / `upperbound`）。
  内置引擎按根着法逐条 yield，皮卡鱼把多行 UCI info 归一成同样的形状，所以调用方
  不必知道背后是谁。**落子只认排名第一那一层**：多线搜索每层都交回信息，拿最后
  那条（往往是 rank 3）去落子等于替对手走棋 —— 这一条写在 `session.py` 的 worker 里，
  也有断言盯着（H3 段）。排名是逐手判分的地基：要给「人录的那一步」打分，
  就得先知道当时最好的那一步是什么。

**存档是投影，不是事件日志**（`server/store.py`）：库里的三张表存「每一局此刻长什么样」，
而不是「谁在什么时候下了什么」。每写一处问的都是同一个问题 —— 这库能不能重放出当前局面、
能不能拿它算出人录的每一步差多少。

- **为什么不是事件日志**。事件日志要把同一份真值写两遍：内存里的 `Game` 一遍，
  追加的流水一遍。两边一旦对不齐（悔棋、认输、排局换局都是会让它分叉的地方），
  对不齐的存档不会报错，它只是**从此每一步都差一行** —— 而 learning 那一层正是靠
  这些行算分的。投影只有一个写入语义：`sync_game(session)` 重写那一局的 `plies`，
  所以写错最多活到下一手。
- **真值只有两样**：`start_fen` 与有序 ICCS 棋谱。`fen_before` / `fen_now` /
  `ply_count` / `state` 全是派生列，断言拿它们和实况逐字段比，比的就是「派生没走偏」。
  ICCS 是身份，中文记谱是显示 —— 重放只认 ICCS。
- **写在哪**：每个 `with self.lock:` 作用域的**最后一条语句**，一共七处（录入、引擎
  应手、新开一局、悔棋、认输、载入排局、清账）。其中最容易被漏的是 worker 那条 ——
  引擎那一手不经过任何公开动词，少这一条就整局都不在库里，而界面看着一切正常。
  按仓库的「牙齿」规矩，故意删掉任何一条 `sync_game`，`verify.py` 的 L 节（12 条）
  必须变红；七处逐个删过，逐个红。
- **换局是换行，不是覆盖**：`new_game` 与 `load` 各发一个新的 `game_id`，排局那局
  标成 `source='setup'`，它的胜负不进「我这盘下得怎么样」那本账；`undo` 不发新 id，
  它改的是同一行。「利用每一局」要的是库里那些**局**，不是最后一局的最后状态。
- **写失败不许把棋下停**：存档坏了不该让人没法录下一步，所以 `sync_game` 吞异常、
  打 traceback、`Store.errors` 计一次数 —— 有一条断言钉住它必须为 0（除那条故意
  抽掉表的破窗测试）。
- **一个进程一本账**：`engine_stats` 是「这个进程一共下了多少」，每次投影都把它整本
  写回 `agg_stats`。所以同进程里开两个会话会互相盖掉最后一笔 —— 服务只有一个会话，
  这没问题；`verify.py` 里有几段断言写的是「记了 1 笔负」这种绝对数，于是那段各开
  一本新档（`_fresh_archive`），否则起点是上一段留下的数。
- **开关**：`EF_STORE=off` 整个关掉，`EF_STORE_PATH` 换位置。默认落在
  `data/elephantfish.sqlite`；`verify.py` / `smoke_http.py` / `.devtools/run.mjs`
  一律指临时文件，自检不许往用户的真档里写测试棋。
- **读侧只接了错题本**：`GET /api/mistakes` 跨历次对局按局面聚合 `plies.review`，
  刻意**不挂会话**（它讲的不是眼下这一局，挂上去就等于给它一把写棋的锁），而且它跑完
  整本库逐字节不变（`verify.py` N 节钉着这件事）。复盘与逐手回放仍然没接 —— 那两条
  要的是「按 ply 取一个历史局面」，目前还没有那条只读路。

**内置 Python 搜索优化**（`engine/search.py`）：MTD(f) 二分换成 PVS + 胜负窗 + 迭代加深；置换表加代际计数器（O(1) 失效，不再 `dict.clear()`）；置换表着法优先试、其余着法懒生成；空着裁剪、LMR、futility 裁剪、静态搜索。着法生成只遍历 90 个真实格点而不是 256 格。

用 `tools/arena.py` 在 1000 个随机开局上跑 50 局回归（深度 5，交换先后手）：

| | 深度 6 耗时 | 深度 6 节点 | 深度 7 耗时 | nps |
|---|---|---|---|---|
| 原版 | 0.71 s | 35.8 k | 12.81 s | ~48 k |
| 现在 | **约 4× 更快** | 大幅下降 | **3.07 s** | ~95 k |

50 局结果：新 24 / 原版 11 / 和 15。**「约 +135 Elo」这行原先写在这里，现在撤了** ——
那把尺子量不出这个结论：老 `tools/arena.py` 让新引擎走 `searcher.think()`，而它的
`use_book` 默认是**开**的，原版那边压根没有这本库，于是带书的一侧开局即中定式，
赢的那部分里多少是搜索、多少是背的，分不开；和棋又被从胜率的分母里踢掉；预算还是
时间，同一台机器换个负载就能漂 2~3 倍。速度那几列是直接计数，不依赖这些，所以留着。
**「优化让引擎变强了，不只是变快」这句要重新量过才配再说**，量法就是下面那把尺子。

**对局度量台第二代**（`tools/arena2.py`）：一把能当「晋级闸门」的尺子，三条硬伤逐条掰过来。

- **A/B 同刻度**。两侧共用同一份配置，开局库只能是显式点亮的变量（`--book`，两侧一起开、
  写进报告），不一致**拒绝开跑**而不是警告。因为「只有都关着才可比」，`Searcher.think()`
  的 `use_book` 默认值从 `True` 翻成了 `False`（`search()` 的没动，产品走棋经接缝显式传，
  界面行为一行都没变）。
- **WDL 含和棋**。胜 1 / 和 0.5 / 负 0，Elo 由同一个分数导出，并给 95% 置信区间。
  自对弈在这个棋力上和棋占一大半，把和棋踢出分母算出来的不是胜率。
- **固定节点预算**。`--budget`：内置在 `search._tick` 的自增点上判（于是 `nodes` 有硬上界），
  皮卡鱼发 UCI 原生的 `go nodes N`。时间随负载漂、深度随战术漂（一连串将军就能顶满），
  只有展开过的节点数两侧同口径、跨机器复现得了。颜色按轮次交替，同一轮两局用同一个开局 ——
  配对设计，开局方差进不了 A/B 之差。
  预算按**两个口径**记：接缝报回来的 `nodes` 是「最后一个完成层」的累计值，而搜索真的
  展开过多少个节点要从 `Searcher` 现场取。两个都得守上界，因为「等预算」这件事只在上界
  是硬的时候成立 —— 这一条当场抓出一个真 bug：内置在收到停表之后还在往计数器里加，
  于是上界漏了 2 个节点。补法是把判断挪到自增**前面**（`_qsearch` / `_negamax` 进门先看停表），
  越线那一拍也立刻问一次，不等到 1024 的整拍。

闸门语义与「不让它替人做主」：样本低于 100 局一律判 `inconclusive`，哪怕 95% CI 的下界
已经 >0 —— 10 局的 CI 半宽约 538 Elo，那个宽度上报晋级是骗人；报告只落到
`data/learned/last_gate.json`，**不自动改 `active.json`**，翻指针是人干的事。基准侧可以是
另一个 git 改动（`--baseline 16483fa`，脚本自己建临时工作树）；那边没有 `max_nodes` 字段时
走 `_tick` 补装，两侧仍然同一个刻度 —— 否则「跟改动前比」这件事一开口就输了。

```bash
python tools/arena2.py --selftest                  # 全套自检，含真下 4 局 + 建基准工作树
python tools/arena2.py --selftest --lite           # 只跑不依赖真对局的那部分
python tools/arena2.py --split gate --games 300 --budget 40000 \
       --candidate HEAD --baseline 16483fa          # 闸门：改动前 vs 改动后
```

`verify.py` 的 M 段默认接 lite（`--arena2-full` 跑全套）—— 判据只写一份，抄进 verify
就有两份，两份迟早分叉，分叉那天 verify 绿的、尺子却是坏的。

**规则修正**：中国象棋的**困毙（无子可动但不是被将军）是判负**，不是和棋。原版沿用了国际象棋的处理，本仓库改正了。

**正确性验证**（`python tools/verify.py`，一条命令跑完，203 条断言，~144s）：

| 固定节点预算（H） | 两个 adapter × 红方走 / 黑方走 × 预算 3000 | `nodes` 不越上界（内置是硬上界，皮卡鱼给它 2% 容差），`use_book=False` 时不许交开局库的手 |

| 存档是投影（L） | 每个动词跑完逐字段比对 + 光靠存档重放棋局 | 库里那一局与实况完全相同；**七处 `sync_game` 逐个抽过，每次都有断言变红**（抽掉 worker 那条：L 节红 2 条，HTTP 第 10 节红 4 条） |

| 错题本按局面聚合（N） | 七局都落在**同一个位置**上（`fen_before` 天生同键），另有一局把带判分的手落在别处作对照 | 门槛只问 `review_verdict` 那一处，自检里不抄第二套判据；错过 / 下对了 / 看不准 / 读不出四档相加恒等于判过分的手数；`at_most`、`uncertain`、`below_top` 一律不进错题；挑「最差那次」先比档再比大小（慢一步杀压过差九兵 —— **把它改回单个数字，这条就红：`2 vs 900`**）；读一整遍之后整本库逐字节不变 |

着法生成那一项是**连顺序都要求一致**的：重写搜索层不允许带来任何规则层面的漂移。
界面侧另有 `.devtools/` 里的八套自检（七套 Playwright 画面 + 一套判分措辞，`npm test`
一条命令跑完），见上方「界面自检」。
对外 HTTP 契约（状态码 / 字段 / 路由 / stale 任务 / 评分字段 / 判分 / 存档落库 / 错题本）由 `python tools/smoke_http.py`
单测，83 条断言 —— 第 10 节是**换一个进程去读那个库**，所以它证明的是「服务起起来之后写路径真的挂在
HTTP 动词上」，这是 `verify.py` 在同一进程里 new Session 那条路证明不了的；第 11 节再把错题本摊开对账：
接口报的每题四档（错过 / 下对了 / 看不准 / 读不出）要与另一个进程直读的库一致，而且读它这件事
本身不许动会话 —— 两次 `/api/state` 除了 `server_time` 与 `analysis.elapsed` 这两个每次现算的
墙上时钟，必须逐字段相同。第 9 节那条「人录的一手有名次与差值」要等判分**收手**再去挑那一手：
排名线是整层整层换的，第 d 层的第 1 名到 d+1 层可能已经掉出前三，抢在冒头那一瞬间挑就会把
自己的窗口感应写成「产品没给分」—— 这类红是自检在跟自己抢跑。

# 特性

1. 使用简单而高效的 MTD 二分搜索算法（见[对弈程序基本技术](articles/对弈程序基本技术.pdf)）.

4. 使用python标准数据结构.
